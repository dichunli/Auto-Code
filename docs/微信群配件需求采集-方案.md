# 微信群配件需求采集进系统（第一版）

## Context（背景）

企业内部用微信群沟通，技师提配件需求的习惯是：**拍车牌/VIN 照片 → 打字说配件名 → 补配件照片**。这些消息散落在群里，采购员靠爬楼翻群，容易漏单。

目标：把 PC 端微信群消息自动采集进汽修管理系统，按"同一人+时间窗"自动归堆成"配件需求包"，采购员在系统页面看一眼、点确认，形成正式需求台账。

**方案选型（已与用户对账确认）**：PyWxDump 数据库轮询方案——不注入微信进程，只读内存拿密钥+解密本地数据库，风险低于 hook 类工具。版本策略：不必锁死小版本，但**关闭微信自动升级**，手动升级前先验证解密可用。项目存续风险（律师函/停更）用"数据全量落库"对冲。

**员工零改变**：不要求按格式发消息，程序顺着"拍照+打字"的现有习惯归堆。

## 本计划范围（第一版）

只做：**采集 → 留底 → 页面归堆展示 → 人工确认成台账**。
不做（后续单独立项）：车牌 OCR 预填（第二版，可复用现有 `src/app/api/vin-ocr/route.ts` 模式）、配件名自动匹配 part_names + 库存联动转领料/采购（第三版）。

## 前置依赖（用户侧，与我开发并行）

1. 一台常开电脑，装 PC 微信 + 登录**专用小号**进群，关闭微信自动升级
2. 装 Python + PyWxDump，手动跑一次解密，确认能读到目标群消息（不通则换方案）
3. 告知员工群消息将被系统存档，写入制度

## 架构

```
常开电脑: PC微信(小号) → Python轮询脚本(增量解密+图片dat解密)
   → POST /api/wechat-ingest (multipart, 带共享密钥)
系统侧: 图片写 UPLOAD_DIR/wechat/日期/ → 消息入 wechat_group_messages
   → 群消息整理页动态归堆 → 采购员确认 → wechat_part_requests 台账
```

## 改动清单

### 1. 迁移 SQL：`supabase/migrations_20260827_wechat_group_messages.sql`

两张表，全部幂等写法 + 索引 + RLS（跟随项目惯例 `auth_full_access`）：

```sql
-- 原始消息表:全量留底,wx_msg_id 防重复推送
CREATE TABLE IF NOT EXISTS wechat_group_messages (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  wx_msg_id TEXT NOT NULL UNIQUE,
  group_name TEXT NOT NULL,
  sender TEXT,
  msg_type TEXT NOT NULL DEFAULT 'text',  -- text / image
  content TEXT,                            -- 文字内容(图片消息为 NULL)
  media_path TEXT,                         -- 图片相对路径(/api/media/ 下)
  msg_time TIMESTAMPTZ NOT NULL,
  request_id UUID,                         -- 确认归属的需求,回填
  ignored BOOLEAN NOT NULL DEFAULT false,  -- 闲聊标记忽略
  created_at TIMESTAMPTZ DEFAULT now()
);

-- 配件需求台账:确认后生成
CREATE TABLE IF NOT EXISTS wechat_part_requests (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  plate_number TEXT,
  part_name TEXT NOT NULL,
  quantity NUMERIC NOT NULL DEFAULT 1,
  remark TEXT,
  status TEXT NOT NULL DEFAULT 'confirmed',  -- confirmed/rejected
  confirmed_by UUID,                         -- 服务端取 user.id
  confirmed_at TIMESTAMPTZ DEFAULT now(),
  created_at TIMESTAMPTZ DEFAULT now()
);
```

索引：`(group_name, msg_time)`、`(request_id)`、`(status)`。与早期草案的差异：消息↔需求的关联用 `messages.request_id` 回填（反向关联）替代 `message_ids uuid[]`，查询更规范。

### 2. 接收 API：`src/app/api/wechat-ingest/route.ts`（新建）

- 参考 `src/app/api/cron/sync-attendance/route.ts` 的共享密钥模式：校验 `?secret=` 对 `process.env.WECHAT_INGEST_SECRET`，不对 401
- POST multipart/form-data：`messages` 字段为 JSON 数组（wx_msg_id/group_name/sender/msg_type/content/msg_time），图片消息附文件
- 图片写盘逻辑复用 `src/app/api/upload/route.ts` 的写法：`UPLOAD_DIR/wechat/YYYYMMDD/时间戳_随机.jpg`
- 写库用 `createAdminClient()`（`@/lib/supabase/admin`，外部程序无 session），`upsert` 按 `wx_msg_id` 冲突忽略（防重）
- 返回 `{ success: true, inserted: n }`；`.env.local` 和生产环境加 `WECHAT_INGEST_SECRET`

### 3. 群消息整理页：`src/app/wechat-requests/`

- `page.tsx`（Server Component，参照 `src/app/follow-ups/page.tsx` 模式）：服务端查未归档消息（`request_id IS NULL AND NOT ignored`，近 7 天）+ 已确认需求台账（分页 20 条），传给 Content
- `WechatRequestsContent.tsx`（"use client"）：
  - **动态归堆**：客户端把消息按"同一 sender + 相邻间隔 ≤5 分钟"分组为建议包（纯前端计算，不改库，规则可调）
  - 每个包显示：发送人、时间范围、文字内容、照片墙（`/api/media/` 路径）
  - 操作：填写/修改 车牌、配件名、数量、备注 → **确认**；勾选消息移出本包（拆包）；整包**忽略**（闲聊）
  - 台账区：已确认需求列表（内联分页，照 follow-ups 写法）
- `actions.ts`（"use server"，遵循 09-api 规范）：`确认配件需求(消息ids, 车牌, 配件名, 数量, 备注)` → `验证用户已登录` → 插 `wechat_part_requests` + 回填 `messages.request_id` → `revalidatePath`；`忽略消息(消息ids)`；确认人取服务端 `user.id`
- 菜单入口加在采购相关导航下

### 4. Python 轮询脚本：`scripts/wechat-poller/`

- `poller.py`：循环执行——PyWxDump 取密钥/增量解密目标群消息 → 图片 dat 解密 → 新消息（含图片文件）multipart POST 到系统 → 游标（最后一条消息时间/ID）存本地 json，断点续推；异常重试 + 日志
- `config.ini`：系统地址、密钥、目标群名（可多个）、轮询间隔（默认 30 秒）、微信数据库路径
- `README.md`（中文）：安装步骤、微信版本注意事项、计划任务开机自启配置方法

### 5. 环境变量

`.env.local`（不入库）和生产服务器 `.env` 加 `WECHAT_INGEST_SECRET=<随机32位>`。
