## 一、背景：为什么做这些

工单详情页是全系统最高频、最核心的页面。原先的性能问题分两类：
1. **操作卡顿**：点按钮/改数据后整页刷新（`router.refresh`）——已基本解决。
2. **首屏加载慢**：远程数据库三趟串行查询 + 白屏——部分解决（骨架屏）。

## 二、已完成（在 `fix/work-order-perf` 分支）

**操作提速（写库成功后只局部更新，不刷整页）：**
- 改备注、客户意见、选质检人、技师派工
- 改价格/数量、选配件分支、配件组数量/备注、采购/到货标记
- 删除配件分支：改用数据库原子函数 `delete_part_branch`（一次事务完成"删除+转移选中"，远程不稳也不会留 0 选中脏数据）

**关键机制：** 自己的改动通过 `src/lib/localEditSignal.ts` 标记，`WorkOrderRealtimeSync` 实时同步据此区分"自己改的 vs 别人改的"——自己的不刷整页，别人的照常同步（保住多人协作）。

**修复的金额 bug（原本潜伏）：**
- 配件组数量：整组共用一个数量，原代码只改第一个分支导致选别的分支时小计算错。
- 删除分支金额残留：被删分支没从小计组件移除，用 `deleted` 广播彻底移除。

**重构与测试：**
- 数据加工逻辑抽到 `src/lib/workOrderView.ts`（`buildWorkOrderView`），page.tsx 从 1881 行降到约 1600 行。
- 配套 `workOrderView.test.ts`，14 个单元测试守住金额/分组逻辑。

**首屏体感：**
- 新增 `loading.tsx` 骨架屏，点工单立即显示轮廓，不再白屏干等。

## 三、待办事项（将来需要时再做）

### 1. 加配件分支（兼"加配件、把分支替换成库存配件"）
- 现状：加分支仍用 `router.refresh` 刷整页，远程慢。
- 难点：加分支入口还兼容"直接加配件""把当前分支替换成库存配件"，几个操作要先厘清区别再设计。
- 建议：参考删除分支的做法（原子操作 + 局部更新），但加分支涉及新行的完整数据，较复杂。

### 2. 派工分成弹窗（`AssignMechanicModal`）三个改进
- ① 手动分成自动补足最后一人：填前面几个，最后一人自动算剩余（两人填80%另一个自动20%）。
- ② 回显已设定的分成方式和比例：再次打开弹窗要显示之前设的（现在每次重置成"平均分配"）。
- ③ 比例之和校验前置：输入时实时提醒必须=100，不要等保存才报错。

### 3. 消除第三趟查询（远程首屏提速，省一次往返）
- 现状：`getWorkOrderData` 三趟串行查询，远程每趟一次往返。
- **已核实可行**：第三趟的5张表——`work_order_item_part_media`/`part_picking_records`/`part_return_records`/`supplier_return_records` 都有外键指向 `work_order_item_parts`；`part_batches` 有外键指向 `parts`。都能用 Supabase 嵌套查询并入第二趟，**第三趟可完全消除，3趟变2趟**。
- **⚠️ 金额风险**：`part_batches` 经 `parts` 间接嵌套，多个分支指向同一库存配件时同一批次会重复，摊平 `inventoryByPart` 时**必须按 batch.id 去重**，否则库存翻倍。
- 建议分两步：先嵌套前4张表（无去重问题），再并入 part_batches（加去重，重点测库存数字/配件图片/领料记录）。

### 4. 全项目类型债（高风险大工程）
- `next build` 跳过类型验证，代码大量宽松类型（`[key:string]:unknown`、`as` 断言）。
- 不影响运行，但将来想补严格类型需**单独立项、单独分支**，一次一模块，优先 `src/lib/` 纯函数。

## 四、重要环境提醒

- **`delete_part_branch` 数据库函数**：本地库和远程库要**各建一次**。SQL 在 `supabase/migrations_20260619_delete_part_branch_rpc.sql`。本地若重置数据库后需重新执行；远程已建。
- **本地/远程切换**：改 `.env.local` 的 `NEXT_PUBLIC_SUPABASE_URL` 等，**切换后必须重新 `npm run build`**（`NEXT_PUBLIC_` 变量构建时固化，光重启无效）。
- **删除/原子操作类**：涉及"多步写库要么全成"的，优先用数据库 RPC 做成事务，比前端多次请求可靠（远程不稳时不会做一半）。
